Planning date: 25 October 2026. Status: implementation backlog, not delivered functionality. The user authorized planning and continuing the existing NMA Notion backlog; no implementation, deployment or real-account migration is authorized by this document.

<b>Product outcome.</b> A user interacts with persistent Ngertiin agents with the applicable capabilities and behavioral fidelity of Hermes Agent. Preserve Grokbot/Nakama-inspired persistent bots, the same identity across private DM and one-owner multi-agent groups, and Muse-inspired automatic goals/proactivity. Conversation is the main interface; no mandatory goal activation form.

<b>Explicit direction change.</b> Applicable Hermes capabilities are now the default adoption scope, with reasoned exceptions. This supersedes the earlier feature-inventory guidance that broad Hermes parity was not a target. The current E2B/custom browser implementation is an observed baseline, not a required future backend. Prefer native Hermes tools and compatible environments; select backend/pin based on reproducible evidence. Do not keep the old browser or engine as an automatic runtime fallback. Preserve historical data, migrations and verification evidence.

<b>Evidence boundary.</b> The user reports nearly all tool calls failing in their usage, especially computer/browser. This is a critical user report, not a measured 100% failure rate. Historical NMA-022 evidence covers a narrow [example.com/browser/file](http://example.com/browser/file) flow, not general browser reliability. Inspection found a narrow native-tool allowlist, text-only skills, max\_turns=8, custom context reconstruction and internal wrappers. The current computer outcome path can settle a returned unknown-outcome error as a receipt; action and post-action observation need separate proof. These are audit targets, not reproduced incident root causes.

<b>Baseline.</b> Inventory: 106 capability families at Hermes commit 7489b22af47ce91b366dde81d5831ea422577498; the earlier comparison snapshot is bda3a363e9695e3f63fce4a7ca85ba17b5fecb61, not an assertion about latest main. NMA-028 must revalidate any chosen upgrade and account for new/removed behavior. Browser-harness/fetch-use were excluded from the existing build; packaging/provenance must be resolved, not silently bypassed. No live reliability suite was rerun while writing this plan.

<b>Decision status.</b> The product direction and reopening backend choice come from the user's explicit instruction. The exact native integration seam, backend, future pin, quantitative SLO thresholds and extra exclusions below are proposals to settle through NMA-028. Explicit user exclusions: Nous service coupling, external messaging channels, Ngertiin CLI/TUI/native apps. Proposed additional exclusions remain visible and must be confirmed or assigned an implementation owner during NMA-028; they cannot be silently counted as satisfied.

<b>What full adoption means.</b> Every applicable family and its supported operations must be reachable, correctly configured, usable and verified through Ngertiin. Code presence, an installed dependency or a successful mock is insufficient. Preserve native schemas/results/continuation where compatible. Adapt only product identity, scope, credentials, persistence and web presentation. Provider/backend variants need a supported-configuration manifest, not simultaneous deployment of every vendor. Every bundled/optional skill and selected connector operation gets its own manifest entry; unavailable required entries remain open. The open plugin ecosystem cannot be frozen into a permanently exhaustive list.

<b>Architecture contract.</b> Hermes remains the sole session/admission/execution/scheduling/cancellation/recovery owner. Ngertiin provides authenticated product entities, scoped domain extensions and projections. A supervisor owns process/volume availability only. Native terminal/browser/code must run inside the selected isolation boundary; profile names alone do not isolate tenants. Grants and privacy checks remain, while arbitrary feature suppression, blanket max-turn limits and new initiative policies are not accepted as architecture shortcuts.

<b>Reliability contract.</b> Persist identity before dispatch, reconcile lost acknowledgements, separate action outcome from observation/delivery, retain unknown outcomes and never blindly replay effectful browser/code batches. Preserve native history/tool lineage and compression. A goal may continue in a linked run from verified work after a crash; this is not a promise to restore arbitrary in-memory execution.

<b>Definition of done for every ticket.</b> Record exact upstream modules/revision/notices; implementation and public/native contract changes; versioned storage/config changes and preservation plan; real behavior/failure/restart evidence; observed limitations and links. A grantable tool must pass a useful task in the application. Tests must prove scope, cancellation and effect semantics. No task is Done merely because source is present. Use English for authored engine/backend technical text; preserve user content.

<b>Acceptance and SLOs.</b> NMA-028 freezes samples, thresholds and success oracles before fixes. Report end-to-end task success, integration-attributable failure, provider failure, recoverable tool failures, unknown effects, duplicate effects, p50/p95 response/progress latency and recovery duration with denominators/uncertainty. Proposed invariant gate: zero observed duplicate effects, cross-owner/context leaks and stop violations in the defined test corpus. This is not a universal zero-error guarantee. Required live cases cannot be replaced with skipped or simulated evidence.

<b>Dependency and delivery policy.</b> NMA-028–039 are new Backlog items with native Depends on relations. Urutan is a recommended topological reading/execution order; independent branches can progress once dependencies pass. Each capability ticket includes its minimal required API/UI and live validation; NMA-038 integrates the whole user experience. NMA-039 closes full adoption acceptance; existing NMA-027 remains the final operator/release decision after it. Prior Done tickets remain historical evidence, not a claim this expanded scope is complete.

<b>Consolidation.</b> At the user's request, the original 30 work packages are grouped into 12 tickets, NMA-028–039. Each ticket contains ordered implementation units, unit-level acceptance and verification; these units are sections, not additional backlog tickets. The initial five draft ticket pages are reused. No duplicate 30-ticket series is retained. Cross-ticket dependencies are minimized to actual prerequisites; native coding does not wait for skill-learning, and each capability includes its own minimal API/UI.
