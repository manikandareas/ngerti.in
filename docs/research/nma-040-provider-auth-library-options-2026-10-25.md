# NMA-040: provider authentication library options

Date: 2026-10-25. Status: source research completed; the native-Hermes-first implementation direction was accepted by the user and recorded in [NMA-040](https://app.notion.com/p/404abdd61873806db119ef3ee29739f7). Exact optional-library adoption and dependency versions remain subject to compatibility evidence. This is not a delivered integration or a completed runtime ADR. No credentials were read and no login/model request was performed.

## Finding and recommendation

NMA-040 should reuse compatible Hermes provider/authentication code rather than implement every provider protocol from scratch. Ngertiin still needs its own authenticated connection records, pending-login state, credential ownership, UI and integration with agent configuration. A provider library cannot supply those product-specific contracts automatically.

Pi is a credible reusable **authentication-only** option, independently of its agent runtime. Its current standalone `pi-ai` package exposes login, refresh and request-auth derivation. A small trusted Node helper using only those operations would not introduce another agent loop or become a competing lifecycle authority. Nevertheless, the inspected Pi version still requires adaptation for Ngertiin's multi-account, durable browser and official ChatGPT identity requirements. Its TypeScript language alone is not a sufficient reason to reject it.

Accepted default selection order:

1. Invoke the pinned Hermes auth/provider primitives through small version-checked integration hooks where they implement the required provider contract; do not copy the entire CLI/dashboard into Ngertiin.
2. Keep owner/connection records and durable orchestration in Ngertiin; use a standards library or official provider SDK for a missing/current contract.
3. Evaluate a pinned Pi auth-only bridge if maintained provider coverage reduces more work than the Node/IPC and remaining browser/identity adaptation adds.
4. Do not adopt a second inference abstraction or agent runtime solely to obtain OAuth login.

The default selection order is recorded in the backlog. It is not proof of provider permission, dependency compatibility or production readiness.

## Hermes baseline

The existing Python runtime already has an `OAuthProviderFlow` registry and a cross-process advisory auth-store lock. Its private JSON writer uses an atomic write with mode 0600 and a protected parent directory. Reusing these mechanisms avoids creating another rotating-token store merely because Ngertiin needs a web settings page. Sources: [auth registry](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/auth.py#L1946), [auth-store lock](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/auth.py#L721), [private store persistence](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/auth.py#L789).

Hermes also defines a configurable OAuth PKCE plugin helper, including a token-request override suitable for a broker integration. Its onboarding is loopback/terminal oriented. The dashboard has start/poll/cancel operations, but pending OAuth sessions are held in a process-memory dictionary and profile checks are not Ngertiin authenticated owner/connection binding. Native primitives are reusable; the complete dashboard is not a turnkey tenant-aware connection service. Sources: [PKCE helper](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/auth_oauth_pkce_plugin.py#L41), [pending sessions](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/web_server_oauth.py#L176), [web operations and profile validation](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/web_routers/oauth.py#L795).

The pinned Codex adapter uses a fixed Codex client ID, `/oauth/token`, and the `chatgpt.com/backend-api/codex` inference route. This is a different contract from the currently documented dynamic Sign in with ChatGPT/public Responses flow. It must not be relabeled as equivalent without adaptation. [Pinned constants](https://github.com/NousResearch/hermes-agent/blob/7489b22af47ce91b366dde81d5831ea422577498/hermes_cli/auth_constants.py#L75). The official provider-specific alternative is described in the [OpenAI Sign in with ChatGPT cookbook](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt), including the `@siwc/local` devkit; SDK fit must be checked against the intended local/hosted access and identity contract.

## Pi: useful without adopting the Pi agent

### Current public auth API

Pi's current `pi-ai` provider owns an `OAuthAuth` with `login(interaction, options)`, `refresh(credential, signal)` and `toAuth(credential)`. Login has caller-supplied prompt/notification callbacks and cancellation. `toAuth` produces ordinary request auth: an API key/bearer value, headers and optionally an account-dependent base URL. These are callable without Pi inference or agent execution. [Auth interfaces](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/types.ts#L206).

Alternatively, `Models.login()` orchestrates a provider login and persists the result to an injected `CredentialStore`; `Models.getAuth()` derives request credentials and refreshes them when needed. The `/oauth` export is now type-only: use provider-owned auth or `Models`, not older global `loginOpenAICodex`/`getOAuthApiKey` examples. [Models login/getAuth](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/models.ts#L756), [current programmatic OAuth guidance](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/README.md#programmatic-oauth).

The injected store is explicitly one credential per provider ID. `modify` must serialize read/modify/write across processes where necessary; `Models` runs refresh inside that operation and persists replacement tokens before releasing it. The built-in in-memory store only serializes within its process. Ngertiin would therefore bind a store to each owner and connection/registration, or supply an equivalent account-qualified adapter; one global provider-keyed store is insufficient for multiple users or multiple accounts at one provider. Direct calls to `OAuthAuth.refresh()` bypass this orchestration and require the broker to own the lock/persistence. [Store contract](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/types.ts#L50), [refresh transaction](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/resolve.ts#L119), [in-memory store](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/credential-store.ts).

### Provider coverage and the remaining adaptation

The inspected source includes OAuth implementations for Anthropic, legacy OpenAI Codex, public Sign in with ChatGPT, GitHub Copilot, OpenRouter, Kimi Coding, Meta, xAI and Radius. This is a technical inventory, not a statement that every option is permitted for Ngertiin. OpenCode Zen/Go remain API-key provider options rather than a generic subscription OAuth solution. [Provider auth loaders](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/oauth/load.ts), [supported providers](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/README.md#supported-providers).

The public ChatGPT implementation is a meaningful advantage over the pinned Hermes legacy path: it requests the direct-plan scope and targets the public API through the OpenAI provider. In this inspected version, however, its browser listener uses fixed loopback port 1455; each login requests a new dynamic client registration; and the source explicitly checks ID-token presence without using it to identify the account. Stable registration reuse, validated user/workspace mapping and a multi-user web callback are not supplied by that implementation. These are version-specific fit gaps, not claims that Pi can never support them. [Registration and loopback constants](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/oauth/openai-chatgpt.ts#L15), [ID-token handling](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/oauth/openai-chatgpt.ts#L200), [login construction](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/oauth/openai-chatgpt.ts#L252), [OpenAI provider](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/providers/openai.ts).

OpenRouter uses a loopback callback or manual redirect/code prompt and returns the account's API key; its refresh operation is a no-op. This output can be mapped to Hermes's existing OpenRouter key path without using Pi inference. Public ChatGPT's bearer token can similarly be consumed by a Python HTTP/SDK transport, but that does **not** make it compatible with Hermes's legacy Codex route: public Responses request fields, streaming, tool schemas, scopes and account identity still need integration proof. [Pi OpenRouter auth](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/oauth/openrouter.ts), [request-auth shape](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/src/auth/types.ts#L8).

Pi's OAuth implementations are Node-only. A Python integration therefore needs a small subprocess/service boundary or a maintained port. A viable auth-only helper would expose login/refresh/disconnect operations bound to trusted owner/connection identifiers and return versioned credential results or scoped request auth to the trusted broker. It would have no model loop, tools, conversation session owner, scheduler or recovery policy. Cross-language IPC, secret handling, pending-login durability, restart and simultaneous-login behavior must be measured before choosing it. [Browser/runtime guidance](https://github.com/earendil-works/pi/blob/d5b3de22d0e24a3e9c38a9410d3329b099717283/packages/ai/README.md#browser-compatibility-notes).

Assign exactly one credential/refresh writer for each connection. If the auth helper owns rotation, Hermes consumes its authorized request credential and must not independently refresh the same grant; if the trusted Python broker owns rotation, direct helper calls operate under that broker's lock and commit policy. Two independent stores or refresh owners would undermine the rotating-token guarantees of either library.

## Other libraries

**Authlib is the closest Python-native standards helper.** Its async OAuth client supports token exchange/refresh and an application-supplied token-update callback; Starlette/FastAPI integrations adapt browser callbacks. It does not provide a ready-made ChatGPT/OpenRouter/OpenCode model-provider connection catalog or their commercial entitlement rules. The inspected `1.9.1` implementation imports `httpx2`, so compatibility with Ngertiin/Hermes's existing dependencies must be tested rather than adding an unpinned dependency. [Stable HTTPX2 guide](https://docs.authlib.org/en/stable/oauth2/client/http/httpx.html), [async client source](https://github.com/authlib/authlib/blob/914229f261602e3de17ac50dd47d4c54b9fbec8d/authlib/integrations/httpx_client/oauth2_client.py#L67), [framework callback implementation](https://github.com/authlib/authlib/blob/914229f261602e3de17ac50dd47d4c54b9fbec8d/authlib/integrations/starlette_client/apps.py).

**Vercel AI SDK is primarily an inference/provider abstraction for this decision.** The inspected OpenAI provider accepts a supplied key and turns it into a bearer header. That does not perform user login, retain registrations or implement Ngertiin connection ownership. Its experimental harness package has OAuth token-refresh utilities, but adopting `HarnessAgent` would add an unrelated execution/session abstraction. Neither is necessary merely to connect OAuth to the current Python Hermes runtime. [OpenAI provider](https://github.com/vercel/ai/blob/682e2dd71456f14f9da33a1b983d1998c3a1184c/packages/openai/src/openai-provider.ts#L179), [harness OAuth utility](https://github.com/vercel/ai/blob/682e2dd71456f14f9da33a1b983d1998c3a1184c/packages/harness/src/utils/oauth-access-token.ts), [experimental harness](https://github.com/vercel/ai/blob/682e2dd71456f14f9da33a1b983d1998c3a1184c/packages/harness/README.md).

**LiteLLM is useful when a Python inference gateway/normalization layer is itself wanted.** Its inspected ChatGPT authenticator still uses the legacy fixed Codex client/backend endpoint, discovers its token directory from process environment and reads/writes an auth file. It requires interactive device login outside an async proxy/worker if no usable token exists. Thus Python compatibility alone does not solve NMA-040's browser and multi-connection contracts, and swapping to it would duplicate Hermes provider responsibilities. Its xAI adapter also has its own environment-selected credential file and process lock. [ChatGPT authenticator](https://github.com/BerriAI/litellm/blob/dddbaa803d6e9fcc862ea7a5412f771cb1ae040e/litellm/llms/chatgpt/authenticator.py#L55), [legacy route constants](https://github.com/BerriAI/litellm/blob/dddbaa803d6e9fcc862ea7a5412f771cb1ae040e/litellm/llms/chatgpt/common_utils.py), [xAI authenticator](https://github.com/BerriAI/litellm/blob/dddbaa803d6e9fcc862ea7a5412f771cb1ae040e/litellm/llms/xai/oauth.py#L123).

## What remains Ngertiin-owned in every option

- Authenticated owner/connection/account registration identity, account selection and grants to persistent agents.
- Durable pending-login/callback state, expiry/cancel/restart behavior and a callback surface appropriate to the actual deployment.
- Protected credential persistence, rotating-token serialization, disconnect/revocation state and versioned non-secret references.
- Provider-specific eligibility and billing distinctions, catalog versus actual inference access, and errors for quota versus expired credentials.
- Safe handoff of authorized credentials to the single Hermes authority, preserving run snapshots, scope fences and effect semantics.
- Authenticated settings/UI and real provider/inference/tool acceptance in every claimed supported configuration.

No library comparison here establishes provider terms, partner admission or hosted deployment permission. A library implementing a token exchange is evidence of technical behavior only. The OpenAI provider-specific flow and any extra provider restrictions remain the implementation's authoritative contracts.

## Verification boundary and next decision

Verification was static source/document inspection at the revisions above, including the current Pi credential-store API and concrete login/refresh modules. No package was installed, no protocol was exercised against a provider, and no clean-install, login, refresh-race or browser acceptance result is claimed.

The accepted default in NMA-040 is **Hermes-native plus a narrow standards/provider SDK where necessary**. Initial implementation must record the exact native seams, dependency versions and compatibility evidence. Compare a **Pi auth-only helper** only if native contract gaps make its maintained adapters worth the bridge and remaining product work. Use the same required providers to test login, account/registration identity, refresh persistence under concurrency, restart and the Python credential handoff. This work stays inside the existing two-ticket split; it does not require another execution engine or another backlog ticket.
