## Objective

Deliver the planned multi-organization product in the existing web-client conversation interface using the verified backend contract.

The [main server-organizations plan](../architecture/server-organizations-plan-2026-11-12.md) owns the design, scope defaults, diagrams and privacy model. This record is an implementation backlog, not completed implementation evidence. Targets are the server, web-client and Tauri; desktop-rs is paused.

## Implementation units

1. Implement guarded first-owner setup, web login/recovery/invitation acceptance and immediate private default-agent workspace with a library-generated single-syllable name, preserving creation through unavailable AI setup.
2. Add organization switching, My agents/Team agents and permission-aware Settings for members, Workgroups, Team-agent access and connection ownership.
3. Implement private per-user/conversation AI connection selection and clear actual account/model/billing status; keep app installation/grant management in Marketplace.
4. Namespace and reconcile all retained drafts, uploads, pending commands, projections, search/preview caches, SSE cursors and viewers by server/user/organization/conversation.
5. Preserve existing conversation-first navigation, icons, Focus, contextual panels, queue/stop/HITL, Goals/Routine and progressive personalization; build real API error/loading/revoke/empty states.

## Acceptance criteria

- [ ] Owner creates two organizations; an invited Member joins the intended organization with the assigned role/Workgroups and completes a first task without a mandatory personalization wizard.
- [ ] Two members see the allowed Team agent and their own private conversations/memory/files; administration controls do not reveal another member's chat.
- [ ] Organization/account/server switching across tabs, logout and pending submissions cannot send or display another scope's data.
- [ ] A connection change is private to that user/conversation, current billing is visible and an unavailable selection requests explicit action.
- [ ] Real API desktop/mobile browser journeys cover creation, invitations, settings, Marketplace, files/Computer, responsibilities, reconnect and removal.
- [ ] Accessibility, focus, responsive states and screenshots are assessed on rendered surfaces; existing unrelated conversation behavior remains verified.

## Verification and evidence

Playwright or equivalent real-API desktop/mobile journeys, multi-browser actor scenarios, focused component checks and rendered visual review.

At implementation time, retain a report under `docs/verification/nma-080/` with exact source/config/dependency versions, setup, denominator, pass/fail/skip, unknown outcomes and limitations. Preserve fixture, database, native/provider, browser/Tauri and distribution evidence as distinct proof. No such verification is claimed by this planning record.
