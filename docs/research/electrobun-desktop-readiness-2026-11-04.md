# Electrobun desktop readiness for Ngertiin

Research date: 2026-11-04. This is a source and documentation assessment for a macOS development application with a possible later production release. It is not implementation, native verification, a security audit, or a change to the active product roadmap. No Electrobun runtime or application was installed or built. GitHub and official documentation were read directly because Firecrawl had no remaining credits.

Subsequent decision: the user selected Electron for the development application. Implementation and evidence are recorded in [Electron development application](../architecture/electron-development.md). The upstream observations below remain a dated research snapshot.

## Assessment

Electrobun has the documented primitives needed for a bounded development trial: a Bun main process, React/Vite templates, independent webview HMR, windows, trays, cancellable quit, packaged assets, and release tooling. Those capabilities support trying the framework; they do not establish that Ngertiin's long-lived background lifecycle is already reliable. Keep Ngertiin's existing backend as the application authority, and evaluate Electrobun as the desktop host and service supervisor. The exact platform, renderer, runtime, and framework version are part of that evaluation. [Architecture](https://docs.electrobun.dev/electrobun/guides/architecture/overview/), [main-process API](https://docs.electrobun.dev/electrobun/apis/main/), [development loops](https://docs.electrobun.dev/electrobun/guides/hot-reloading/).

For a macOS Bun/React development trial, the recommendation is to proceed only as an isolated evaluation with a pinned stable release. For adopting Electrobun as Ngertiin's production host, startup responsiveness, sleep/wake recovery, instance ownership, transport boundaries, and installed updates are unresolved acceptance work. If minimizing framework-specific lifecycle work is the main priority, this evidence favors retaining Electron as the current baseline while evaluating Electrobun separately; this is an engineering judgment, not a claim that Electron has been tested in Ngertiin.

## Lifecycle and development implications

- Stable source sets `runtime.exitOnLastWindowClosed` to `true` by default. A tray/background application must explicitly choose its last-window behavior. Window hiding, showing, activation, normal close requests, and direct close are documented separately. [Stable BrowserWindow source](https://github.com/blackboardsh/electrobun/blob/v2.0.5/package/src/sdks/main/core/BrowserWindow.ts), [window API](https://docs.electrobun.dev/electrobun/apis/browser-window/).
- `before-quit` is cancellable, but its emitter does not await promises. Required asynchronous backend shutdown/persistence must complete before allowing quit, or the handler must synchronously cancel and explicitly retry after cleanup. This is documented in the stable tag, not just live docs. [Stable event documentation](https://github.com/blackboardsh/electrobun/blob/v2.0.5/docs/src/content/docs/electrobun/apis/events.mdx).
- Vite HMR can reload the webview without relaunching the native host. Whole-app watch rebuilds and relaunches it, resetting main-process state. For Ngertiin, UI edits should normally use the former, while the backend has independent ownership and recovery. A development-server success must later be repeated with packaged `views://` assets. [Hot reloading](https://docs.electrobun.dev/electrobun/guides/hot-reloading/).
- Bun is the default supported JavaScript runtime; Cottontail is experimental and opt-in. The stable compatibility document names packaged Bun `1.4.4`. Ngertiin currently pins a different Bun version, so using the bundled runtime for the backend requires compatibility verification; a separately supervised backend can retain its own runtime initially. [Stable compatibility document](https://github.com/blackboardsh/electrobun/blob/v2.0.5/docs/src/content/docs/electrobun/guides/compatability.mdx).

## Renderer and platform choices

The default renderers are WKWebView on macOS, WebView2 on Windows, and WebKitGTK 4.1 on Linux. Bundled CEF supplies a pinned Chromium implementation at a materially larger distribution size. macOS and Windows can select a renderer per view; Linux selects one implementation for its process. Ngertiin's React client can remain a webview UI; the separate GPU-rendered Electrobun UI is experimental and unnecessary for this assessment. [CEF guide](https://docs.electrobun.dev/electrobun/apis/bundling-cef/), [main-process coverage](https://docs.electrobun.dev/electrobun/apis/main/).

Both macOS architectures require macOS 14+. Builds are host-native; producing all OS/architecture releases requires matching native runners. Linux has additional system-library dependencies. These are deployment constraints rather than evidence that macOS development cannot work. [Compatibility](https://docs.electrobun.dev/electrobun/guides/compatability/).

Live Unreleased notes list a macOS native-UI deadlock, a Linux CEF initial-navigation race, and Linux native-UI focus fixes. They must not be counted as stable fixes without a release/source check, and native-UI bugs must not automatically be assigned to React webviews. [Unreleased changelog](https://docs.electrobun.dev/electrobun/guides/changelog/unreleased/).

## Privilege and update boundaries

Stable BrowserWindow source defaults the framework `sandbox` option to `false`; its comments define that option as disabling privileged RPC for untrusted views. Do not equate that switch with a full OS sandbox. Remote pages should receive no privileged RPC surface and should have explicit navigation restrictions. [Stable BrowserWindow source](https://github.com/blackboardsh/electrobun/blob/v2.0.5/package/src/sdks/main/core/BrowserWindow.ts), [window security guidance](https://docs.electrobun.dev/electrobun/apis/browser-window/).

Issue [#518](https://github.com/blackboardsh/electrobun/issues/518) is an open local-RPC transport hardening report. Exact stable `v2.0.5` source still retains the large frame limit and a connection upgrade based on an existing view identity without separate per-view upgrade authentication; binding is already loopback. Message encryption/authentication is a separate layer and is present. This supports a current hardening concern involving local disruption; it does not establish arbitrary RPC forgery or remote code execution. No reproduction was attempted. [Stable core source](https://github.com/blackboardsh/electrobun/blob/v2.0.5/package/src/core/main.zig), [message encryption](https://github.com/blackboardsh/electrobun/blob/v2.0.5/package/src/sdks/main/core/hostTransportEncryption.ts).

Hutch emits native installers, full update archives and optional delta patches; static HTTPS hosting is sufficient. Updates use staged replacement and rollback. The documentation explicitly says the release-routing hash is not content authentication or a signature, so release authenticity still depends on trusted HTTPS hosting and platform signing. [Distribution](https://docs.electrobun.dev/electrobun/guides/bundling-and-distribution/), [update publishing](https://docs.electrobun.dev/electrobun/guides/updates/).

macOS canary/stable signing and notarization are integrated; development builds skip those steps. Windows release signing is not currently integrated into Hutch's packaging pipeline. [Code signing](https://docs.electrobun.dev/electrobun/guides/code-signing/).

The stable changelog reports certificate mitigations in packaged Bun and build tooling, while saying the bundled CEF release still awaits its permanent compromised-certificate blocklist fix from upstream prebuilts. System webviews use OS trust. This is a renderer-specific production consideration, not proof that the Bun path lacks those patches. [Stable release notes](https://docs.electrobun.dev/electrobun/guides/changelog/v2-0-5/).

## Required proof before choosing it for Ngertiin

These are proposed acceptance cases, not tests performed in this research:

1. Repeated cold launches, input responsiveness, double launch, and attach to an already-running backend.
2. Close/reopen and tray behavior while a run or Routine is active, with no second application authority.
3. Laptop sleep/wake, renderer reload/crash, backend restart, and event-stream reconnection without duplicate dispatch.
4. Asynchronous Quit cleanup, persisted state, native-session recovery, and handling of effects whose outcome is unknown.
5. React/Lexical input, streaming, uploads/downloads, provider login, and Computer viewer behavior on the chosen native renderer; compare CEF only if needed.
6. A normal bundled development build as well as Vite HMR. Production additionally needs installed-app update/rollback, data preservation, signing, and supported-platform acceptance.

Passing a small macOS development trial would justify further evaluation. It would not close later production acceptance or establish reliability on the other platforms.
