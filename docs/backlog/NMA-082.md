## Objective

Provide a reproducible owner-operated central server setup with PostgreSQL, supported harnesses, private execution domains, secure ingress and verified recovery.

The [main server-organizations plan](../architecture/server-organizations-plan-2026-11-12.md) owns the design, scope defaults, diagrams and privacy model. This record is an implementation backlog, not completed implementation evidence. Targets are the server, web-client and Tauri; desktop-rs is paused.

## Implementation units

1. Pin the supported server OS/architecture, Bun/dependencies, PostgreSQL image/patch, Codex/Muse executables and Cua image/service tuple; prove native compatibility on that target.
2. Provide a reproducible deployment/configuration path for application, PostgreSQL and execution-domain services, with private storage, readiness and operator bootstrap.
3. Configure HTTPS proxy/SSE/uploads/viewer upgrades, trusted origins/proxies, limits and restricted control/database endpoints. Document URL/callback/certificate configuration.
4. Implement and rehearse coordinated database/blob/credential/domain-volume backup and restore, cutover/rollback, migration upgrades, redacted diagnostics and declared RPO/RTO.
5. Document optional VPN/Tailscale as operator-owned infrastructure, plus measured domain capacity, admission and operational health without adding a VPN SDK.

## Acceptance criteria

- [ ] A clean declared server environment starts the documented stack and supports remote web/Tauri access over certificate-validated HTTPS.
- [ ] Database, harness and Cua control endpoints remain private; application sessions and viewer grants are required in direct and VPN deployments.
- [ ] Both required native adapters and execution-domain isolation are exercised on the deployed target; images/binaries alone are not compatibility evidence.
- [ ] A real restore recovers consistent database events/receipts, artifacts, provider refresh state and private working data without cross-tenant reassignment.
- [ ] Upgrade failure and rollback are rehearsed with preserved data and a single lifecycle authority; unrelated existing state is untouched.
- [ ] Runbook records resource workload, observed limits, setup versions, actual RPO/RTO and unverified platform or provider conditions.

## Verification and evidence

Isolated server deployment rehearsal, HTTPS/API/SSE/viewer checks, real native tools, backup/restore and rollback with named disposable data.

At implementation time, retain a report under `docs/verification/nma-082/` with exact source/config/dependency versions, setup, denominator, pass/fail/skip, unknown outcomes and limitations. Preserve fixture, database, native/provider, browser/Tauri and distribution evidence as distinct proof. No such verification is claimed by this planning record.

NMA-081 retains two intermittent pinned authentication schema-introspection startup failures whose cause remains unconfirmed; its current backend cohort and 80 isolated startup probes pass. Reproduce and diagnose that setup limitation on the declared deployment target before readiness claims. Its local HTTPS/media proof also leaves deployed WSS proxy upgrades and coordinated shutdown/recovery unverified. See the [NMA-081 limitations](../verification/nma-081/README.md#limits).
